# 重构模式服务器端契约

本文档定义服务器与小车在重构模式下的通信约定。目标是避免“协议理解不一致”导致的准备卡住、图像同时上报、掉线误判和时序死锁。

## 1. 总体原则

1. 服务器是重构流程的调度者，小车是执行者。
2. 准备阶段优先保证全车可见，不要提前切换会屏蔽前车状态的拓扑。
3. 拼接阶段同一时刻只允许 1 辆车主动发送图像。若必须并发，建议并发上限为 1。
4. 服务器收到某辆车的图像后，应优先针对该车生成 `GUIDE`，不要等待其它车辆的图像再统一处理。
5. 服务器应将 `PREP_OK`、`STEP_OK`、`STEP_FAIL` 视为阶段性控制信号，并记录时间戳。

## 2. 推荐时序

1. 服务器广播 `[R,PREP]`。
2. 服务器广播 `[R,ORDER,CAR1,CAR2,CAR3,CAR4]` 或实际顺序。
3. 各车进入准备阶段，按自身序号寻找前车状态，收到位置满足阈值后回 `PREP_OK`。
4. 服务器等待所有车的 `PREP_OK`。
5. 服务器逐车下发 `[R,STEP,CARn,POS=HEAD|MID2|MID3|TAIL]`。
6. 该车开始上传 `IMG_META` 和 `IMG_CHUNK`。
7. 服务器解析图像后，向该车下发 `[R,GUIDE,CARn,VX=...,VY=...,VZ=...,DONE=0|1]`。
8. 服务器在 `DONE=1` 时结束该车拼接，等待或推进下一车。
9. 所有车完成后，下发 `[R,DONE]` 或进入分离流程。

## 3. 准备阶段要求

服务器必须明确以下规则：

1. `ORDER` 要在 `PREP` 之后尽快下发，并且必须是四辆车的完整序列。
2. 小车准备目标是“前车后方固定间距”，不是相对于绝对坐标的全局点。
3. 准备阶段依赖前车状态，因此若拓扑已启用，必须保证后车仍能接收前车广播。
4. 若某辆车长时间未回 `PREP_OK`，优先检查前车状态是否可见，而不是直接认为该车故障。

推荐服务器处理：

1. 维护一个 `prep_waiting` 状态表，按车记录最后一次收到的前车状态时间。
2. 若 3 秒内没有某辆车的 `PREP_OK`，先发一条重试型 `PREP` 或重新广播 `ORDER`。
3. 如果场地或视觉条件导致排序需要调整，服务器必须同步更新 `ORDER`，不能只改一半。

## 4. 图像上报要求

图像协议分为两部分：

1. 文本头 `IMG_META`。
2. 原始二进制分片 `IMG_CHUNK`。

规则：

1. `IMG_META` 必须先发，之后才是 `IMG_CHUNK`。
2. `IMG_CHUNK` 只能携带原始 JPEG/图像字节，不能再做 Base64 或其他二次编码。
3. 服务器要按 `SEQ + IDX + TOT` 重组同一帧，不允许跨帧混拼。
4. 若发现 `IDX` 不连续、`TOT` 不一致、`SEQ` 变化，整帧丢弃并要求车端重发。

建议服务器解析字段：

1. `SEQ`：帧序号。
2. `W/H`：图像宽高。
3. `LEN`：整帧字节长度。
4. `IDX/TOT/SZ`：当前分片序号、总分片数、当前分片大小。

## 5. GUIDE 指令要求

服务器下发给单车的 `GUIDE` 应满足：

1. 只针对当前正在拼接的那辆车。
2. `VX/VY/VZ` 表示小车局部速度控制量，方向定义需与车端一致。
3. `DONE=1` 表示服务器认为该车当前阶段已完成，小车应立即减速停车并回 `STEP_OK`。
4. `DONE=0` 表示继续执行，不应提前结束。
5. 如果服务器连续一段时间不再下发 `GUIDE`，车端会进入超时保护，因此服务器必须保持刷新。

建议服务器侧节拍：

1. 每 50~100 ms 刷新一次 `GUIDE`。
2. 若视觉算法暂时无解，也应发送零速度或小速度保活，而不是完全停止发送。

## 6. 拓扑策略

推荐策略是：

1. `PREP` 阶段使用全连通或至少保证链路可见性。
2. `STEP` 阶段仍建议保持前车可见，以便准备和拼接过程中读取前车状态。
3. 只有在所有车都完成 `PREP_OK` 且服务器确认不再依赖全局状态后，才切换更严格的拓扑过滤。

如果必须提前启用拓扑过滤，最低要求是：

1. 每辆车都能收到它前车的广播状态。
2. `ORDER` 与拓扑矩阵必须一致，不得出现“顺序里有前车，但拓扑把前车屏蔽了”的情况。

## 7. 失败与恢复

建议服务器支持以下处理：

1. 收到 `STEP_FAIL` 后，先暂停当前车拼接流程，不要继续下发该车的 `GUIDE`。
2. 若失败原因为图像/链路超时，允许该车重新进入 `STEP`，但要重新分配帧序号或清空缓存。
3. 若失败原因为准备超时，优先检查拓扑、`ORDER`、前车状态广播是否完整。
4. 若某车离线，服务器应从 `ORDER` 中临时移除或将其标记为不可用，再重新计算后续流程。

## 8. 服务器实现最小检查清单

1. `PREP` 发送后，至少等待每车 `PREP_OK`。
2. `STEP` 逐车串行下发。
3. 图像按 `IMG_META -> IMG_CHUNK` 方式重组。
4. `GUIDE` 持续刷新，直到 `DONE=1`。
5. 记录每辆车最后一次心跳、`PREP_OK`、`STEP_OK`、`STEP_FAIL` 时间。

## 9. 本端约束

当前车端已经按如下方式工作：

1. 准备阶段依赖前车状态。
2. 拼接阶段会按顺序错峰上报图像，减少同时发送的冲突。
3. `GUIDE` 超时会触发失败保护。
4. 结束拼接后会立刻停车并上报结果。

如果服务器实现与以上约定不一致，最容易出现的现象就是：

1. 永远差一辆车收不到 `PREP_OK`。
2. 所有车在同一时刻进入拼接后，网络短时间拥塞并误判掉线。
3. 服务器等“全部图像”而不先处理单车图像，导致 `GUIDE` 死锁。
